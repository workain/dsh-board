# DSH Board

A local task board for [DeepSeek Harness](https://www.npmjs.com/package/@deepseek-ai/dsh). This repository contains an **early development preview**, not a stable, production-ready or security-certified release.

## Preview scope

- Create local boards, columns and tasks; change task title, description and column.
- See available boards on opening the panel and open one in a click; optionally filter by workspace, use a board or list view and search or filter local tasks by column, assignee and presence of a linked session in the selected workspace. Local assignee is a free-text value, not a verified account identity. Boards have a synchronized horizontal scrollbar above the lanes; empty lanes are hidden without changing their statuses, and local statuses remain editable through **Manage statuses**. Task drawers can be resized by dragging their left edge or using the focused separator's arrow, Home and End keys. Column whale controls count distinct linked sessions and toggle the linked-session filter. Card whale controls open a linked session or a menu when several are linked. Ctrl-click (Cmd-click on macOS), or middle-click, opens the chosen available session in a new browser tab; the original tab stays on the board.
- Link a local task to an existing session in the selected workspace and open it. To start from a session, type **`/board`** with no arguments, choose a local board, then **Link this session** on an existing task. This is a client action, not a model request; the session must belong to the board's workspace. It does not create a task. Do not append arguments: this DSH version may send an unrecognized argument-bearing slash line to the model as a prompt.
- `board_link_session` lets an agent request an explicit one-time user approval to link or unlink **its own** session.
- Local boards work without network access. An optional Yandex Tracker connection uses the Host's credential provider and provides a partial board view, issue drawer and workspace-session links. Tracker cards link to the issue on `tracker.yandex.ru` and have whale session shortcuts; column controls and horizontal scrolling are also available. Tracker agent tools use trusted Full access (`danger-full-access`) for writes when that mode is active; otherwise they retain one-time approval requirements. Access, membership, version and unknown-outcome checks still apply. GitHub integration is not implemented.

The local domain model also contains iterations, labels and comments, but this preview does **not** yet expose them in the UI or agent tools. Shared-board assignment, default board, deletion and cross-workspace/session-without-workspace linking are not exposed yet. Agents cannot create or edit local tasks through tools in this preview. The full project design and future integrations are broader than this preview.

## Requirements and installation

- DeepSeek Harness **0.2.1-rc.5**; other versions are not yet tested.
- Node.js **24 or newer** with `node:sqlite` available (this Node API reports itself as experimental).
- A POSIX, local, same-host filesystem, a single trusted OS user and a writable DSH home. Windows, network filesystems and multi-user isolation are not supported by this preview.
- Harness services: Connection, WorkspaceRegistry, Tools, Approval; without them Cordis will not activate the plugin.

Install the bundle directory using the Harness Plugin Manager (`install_bundle`); the manager updates the selected profile and can affect all its sessions. Review the code before enabling any Host plugin. Do not edit the profile's package or patch files by hand. If replacing an already installed package, a Host restart may be required. Check the manager's activation result rather than assuming installation succeeded.

The original authoring instructions for this DSH build require using the Plugin Manager instead of manually modifying profile files. The `npm run build` command checks syntax, package completeness and that generated browser helpers match their source; it is not a generated Typert RPC or browser build. After changing `tracker-markup.mjs`, `tracker-statuses.mjs` or `session-card.mjs`, explicitly regenerate the checked-in client helper block with `node scripts/build.mjs --write`. Package-manager scripts are not required.

## Storage and security limitations

The plugin owns a dedicated SQLite database at `$DSH_HOME/storages/dsh-board/board.sqlite` (`~/.dsh` if unset). Its directory must be canonical, owned by the running user and mode `0700`; the database must be mode `0600`. SQLite transactions compare revisions under `BEGIN IMMEDIATE`, so conflicting writes to the **same database** fail rather than silently overwriting. All writers must use the same absolute path on a local filesystem. Changing the database, SQLite journal mode, its directory or sidecars outside the plugin is unsupported. The checks do not defend against an adversarial process running as the same OS user. Do not point this dedicated path to an unrelated database: SQLite may recover a hot journal before the schema check.

Initial creation is fail-closed. A crash during first initialization can leave an empty or unsupported file and the plugin may refuse to start. Do not delete it automatically: stop all writers, preserve a backup, verify with the owner that no data exists, then explicitly recover or recreate it. A simultaneous first open may also require retry. `synchronous=FULL` is not a proof against every power failure; power-loss and filesystem fault tests remain open. SQLite's synchronous lock wait can block the Host event loop for up to five seconds.

The HTTP endpoints are registered with DSH Connection, whose authenticated exact-route dispatch denies non-owner peers. They are **not** multi-user resource ACLs; snapshots contain owner-visible board and link data. The owner POST endpoint cannot distinguish a human's explicit GUI action from a process with owner credentials. It does not itself prove human consent. Agents must not invent columns, statuses or categories or reclassify tasks by their own interpretation without explicit user consent; when copying, preserve the source structure and statuses or ask first. Merely accessing Tracker does not authorize changes. A same-UID process with unrestricted access can bypass application controls by modifying the database directly, so this behavioral rule is not a security boundary. A session's membership is checked through the Host's workspace registry, which is a cached per-process view. Multiple DSH Host processes sharing one home can have inconsistent workspace membership even though the board database prevents lost updates; run only one Host per DSH home until cross-process membership synchronization is verified. Archive/unarchive and workspace changes can race linking. The agent tool requires the Host approval service and one-time approval; approval events may contain target IDs in the session log. SQLite commits and session-log approval events are not one atomic transaction.

Correctly routed POST bodies are limited to 64 KiB, the stored aggregate to 4 MiB and a projected snapshot to 8 MiB. Concurrent handler requests and pending operations are bounded; this is a small-board preview, not a load-tested capacity claim. The DSH HTTP carrier can buffer unmatched methods and GET request bodies before the plugin handler, up to its separately configured global limit; these plugin limits do not bound that carrier-level exposure. Restrict access to trusted owner clients and configure carrier limits as appropriate.

Drafts and uncertain-operation protection live only in browser memory. Closing or refreshing the page can discard drafts **and the unknown-outcome flag**. Never automatically retry a write with an unknown outcome: independently check its result before any retry, even after a page refresh. During the same page lifetime, a successful refresh may be followed by a request for explicit acknowledgment before another write; an old request may still win the revision race. There is no durable operation idempotency or guaranteed exactly-once behavior.

The new-tab session handoff is a plugin-owned fragment, not a built-in Harness deep link. The destination checks workspace membership, available sessions and the connection before opening, then removes the fragment; the authenticated Host remains authoritative. Session lists are cached and may be stale after refresh failures. DSH also shares its last-restored session selection between tabs via local storage: opening a new tab does not navigate an already-running board tab, but can affect which session a later reload restores.

The plugin stores local data in plaintext SQLite. Same-UID agents can access it. The optional Tracker integration can fetch private issue titles, descriptions, comments and assignee names visible to the configured Tracker account; they remain untrusted data and are not rendered as HTML. Security questions or vulnerability reports must not include credentials or private task content.

## Yandex Tracker (preview)

Tracker is an optional profile-level connection. The Host resolves `YANDEX_TRACKER_TOKEN` and `YANDEX_TRACKER_ORG_ID` through the DSH credential provider, not from the browser or board database. The token must already grant Tracker access; an OAuth App ID alone is not a token. Choose the organization type (Yandex 360 or Yandex Cloud / Identity Hub), then choose one or more available Tracker boards separately for each DSH workspace in the Board settings. After a Host restart, the plugin automatically restores a previously confirmed selection only after rechecking the current Tracker account, workspace incarnation and access to each exact selected board. A renewed token for the same verified account can be used; the token itself is never stored. Legacy selections lack account provenance and require a one-time owner confirmation. A different account or replacement workspace also requires confirmation; a temporary verification failure leaves data hidden and can be retried without changing the saved selection. Selecting new boards still requires a fresh board listing. Tracker's account UID is assumed stable for this purpose, although its documentation does not explicitly guarantee immutability. Other profiles have separate settings. DSH's local credential store does not isolate same-UID processes.

The adapter reads board metadata, columns and a bounded approximate issue search, including the assignee's Tracker ID and display name when available. The Board view groups by actual Tracker statuses found in the board configuration and loaded issues; statuses with no loaded tasks are hidden from the lanes but are not changed in Tracker. This status-oriented layout can differ from Tracker's board columns; it does not create or change statuses. Board listings, issue search, comments and session-link views are bounded and may be incomplete; treat them as **partial**, even when empty. `filter.boards` is verified against each returned issue's `boards` field but its recall and equivalence to the Tracker UI are not guaranteed. Permissions, concurrent changes, arbitrary columns, sprints and paging can further limit the view; issue search is capped at 500. Comments are requested in sequential pages of up to 100; the interface reports whether traversal has ended or remains incomplete. Tracker can recalculate pages between requests, so even a finished traversal is not an atomic snapshot. Filters apply to loaded results, not all Tracker issues. Tracker issues are not classified as unlinked from an incomplete link view. External Tracker issue content is not copied into local board state. This preview supports OAuth token type and IPv4-only network transport, with standard TLS validation. No separate OAuth app authorization flow is implemented yet.

The session header's Board button opens the same editable Tracker issue card in the right sidebar as the full Board, after validating the session's link and the selected board. Local historical links remain a separate view. Session-link and Tracker checks are point-in-time; a remote operation already dispatched cannot be undone if access changes concurrently. Session-to-issue discovery resolves stored issue IDs against the selected boards, rather than relying only on the partial board search. It is still bounded to 100 IDs, can omit inaccessible issues, and is not an atomic Tracker snapshot. Open an issue card on the Board to use its editable drawer. **Save fields** updates the title, description and/or assignee conditionally on the issue version; editing is unavailable without a usable version. **Change status** checks the selected available transition and its target, then asks for confirmation; some transitions require additional fields that this UI cannot supply. **Add comment** posts a new comment, existing comments can be edited, and **Save session link** links or unlinks a session locally. These are separate, explicit operations, not one atomic Save button: saving one does not save the other drafts. A comment draft can also be queued as a user message to explicitly selected linked sessions after confirmation; queueing may start or resume their agents, and acceptance does not mean the requested work completed. Each recipient is sent separately, so partial success and unknown outcomes are possible. Check the session before attempting an uncertain send again; browser-lifetime duplicate guards do not persist across reloads, tabs, or other clients. Session and workspace membership and Tracker access checks are point-in-time, not an atomic cross-service transaction. Existing-comment editing uses a best-effort version check, not an atomic compare-and-swap, so concurrent edits could still be overwritten. Description and comment previews render a conservative, bounded subset of Markdown and legacy Tracker HTML as safe text and elements; unsupported YFM constructs are shown literally. Images and embedded media are not fetched. Editors retain the original source text. Creating Tracker issues is not implemented.

Tracker session links are stored separately from local board data, keyed by Tracker's immutable issue ID rather than its mutable key. They are scoped to the profile, an HMAC-derived account/tenant identity, and the current workspace and its incarnation. The plugin freshly verifies access to the selected Tracker board and issue and checks workspace membership when using links; cached selections alone do not authorize access. Only sessions in the current workspace are eligible; archived sessions are unavailable for navigation. Link results can omit unavailable entries, and a listed link does not guarantee that its session can be opened. The key-to-ID check and a subsequent remote operation addressed by issue key are separate API calls: a key change or reuse between them is a time-of-check/time-of-use race, not an atomic identity guarantee. Remote Tracker operations and local link updates are not one transaction.

While a Tracker board is open in the active visible panel, the client periodically re-reads its status, columns and partial issues. Updates pause when the page or panel is hidden and resume after returning; this is not background synchronization of every board or a guarantee of immediate changes. The last successful read is shown in the panel. For local tasks, a link counts for filtering when its session ID is currently listed in the selected workspace, regardless of whether the session catalog can open it.

Agent Tracker tools run only for the calling session's workspace and its explicitly selected, currently authorized Tracker boards. `tracker_current_workspace` discovers the calling session's unique workspace and selected boards without guessing a workspace ID from a folder name. They recheck workspace membership, account identity and issue membership before use; these checks and a remote Tracker change are not one atomic transaction. Without trusted Full access, creating a task, changing its fields, adding comments, changing status and linking or unlinking the calling session each require one-time DSH approval. Trusted Full access (`danger-full-access`) suppresses only that manual approval; workspace, membership, version, link-CAS and unknown-outcome checks remain mandatory. The owner can explicitly enable unattended task creation in Tracker settings for one workspace and the current Tracker account; this setting is off by default. While enabled, a verified live root session may create Tracker tasks without per-task approval, including under policy `never`. Delegated agents cannot use this exception. Other operations still require approval. Untrusted input can influence an agent and cause unintended task creation, including into an explicitly chosen queue, within the connected account's permissions; the owner can revoke the setting, including while the Tracker binding is unavailable. The setting is scoped to the profile, account namespace and workspace incarnation; it does not grant Tracker permissions or bypass workspace and board checks. Creating a Tracker task uses the selected board's reported default queue or an explicitly supplied queue key; a queue selected explicitly is not necessarily associated with that board, and creation does not guarantee the task appears on it. If the board response omits its default queue, the plugin reports that the default is unavailable rather than inferring that no queue is configured. With unattended creation disabled, approval policy `never` rejects task creation before dispatch; it cannot be approved interactively in that policy. Session links are shared across selected boards in the same workspace/account. The proposed comment text and the approved target transition are shown in that approval, and tool inputs, outputs and approval events may persist in the session log; do not put credentials into them. Tracker content is untrusted data, not instructions. A rejected approval makes no write. If a network timeout, cancellation or malformed response occurs after sending a change, the outcome can be unknown: check the issue before any retry; no exactly-once guarantee is made. DSH PTC calls can surface a generic aborted error instead of the tool's uncertainty warning, so treat any aborted write as potentially applied. Some workflows require additional fields and cannot be executed by the simple transition tool. Writes need an existing Tracker token with appropriate permissions; this preview does not implement a new OAuth consent flow. Same-UID agents and other trusted Host plugins are not isolated by these checks.

Tracker settings and session links use separate SQLite databases under the plugin's private directory, scoped by launcher profile. Older plugin versions cannot read settings containing the new board-authorization provenance or unattended-creation fields. Keep a compatible backup before upgrading; do not downgrade the plugin against a newer settings database without a verified restoration or migration plan. The account/tenant scope for links uses a durable per-profile HMAC key and the Tracker account UID. The UID is assumed unique for this purpose, but the available documentation does not explicitly promise it is immutable. Protect and back up the profile's HMAC key and link database together; restoring only one or replacing the key can make existing links inaccessible under their original scope. As with local boards, first creation fails closed: a crash can leave an empty or unsupported file that must be investigated without automatically deleting potentially valuable data. API errors are sanitized and no credentials are accepted from browser requests.
